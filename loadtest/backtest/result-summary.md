Gateway와 JWT 처리시간을 제외하기 위해 market-service의 `8082` 포트를 직접 호출했다. 두 revision은
별도 Git worktree에서 동일한 Docker 인프라와 테스트 데이터를 사용해 순차 실행했다. 각 버전을 1회
워밍업한 뒤 동시 사용자 10명, ramp-up 1초, 사용자당 1회 요청 조건을 3회 반복했다.

E2E 완료시간은 처리량 분모에 포함하지 않았다.

## 중앙값 비교

| 지표 | 동기 | 비동기 | 변화 |
|---|---:|---:|---:|
| POST 평균 응답시간 | 27.1 ms | 12.0 ms | 55.7% 감소 |
| POST p95 응답시간 | 37 ms | 23 ms | 37.8% 감소 |

| POST 처리량 | 14.01 req/s | 14.31 req/s | 2.1% 증가 |
| E2E p95 완료시간 | 315 ms | 580 ms | 84.1% 증가 |

| 오류율 | 0% | 0% | 동일 |

비동기 전환으로 생성 API의 응답 대기시간은 줄었지만 계산 자체가 빨라진 것은 아니다. 비동기 버전의
E2E 결과에는 전용 Executor 대기와 250ms 상태 폴링 간격이 포함되어 동기 버전보다 길게 측정됐다.

## Executor 경계 확인

| 조건 | POST 성공 | 완료 확인 | POST 오류율 | POST p95 | E2E p95 |
|---|---:|---:|---:|---:|---:|
| 60 threads, ramp-up 1초 | 60/60 | 60/60 | 0% | 42 ms | 580 ms |
| 60 threads, ramp-up 0초 | 57/60 | 57/60 | 5% | 68 ms | 686 ms |

ramp-up 1초에서는 60건 모두 완료됐다. 반면 60건을 동시에 제출한 버스트 테스트에서는 POST 3건이
HTTP 500으로 실패했다. 이는 `maxPoolSize=5`, `queueCapacity=50`인 Executor의 수용량 경계에서 발생한
결과로 볼 수 있으나, 이 실행에서는 서버 로그를 별도 파일로 보존하지 않았으므로 구체적인 예외 유형은
추가 재현으로 확정해야 한다. 성공한 57건은 모두 `COMPLETED`까지 확인됐다.

## 검증 중 발견한 입력 조건

최초 5년 범위(2021-01-01 ~ 2025-12-31) 테스트는 비교 대상 revision의 최대 조회 기간 365일 제한으로
HTTP 400을 반환했다. 구현 성능과 무관한 유효성 검증 실패이므로 공식 비교에서 제외하고, 두 버전 모두
허용하는 2025년 1년 범위로 다시 측정했다.

## 결론

- 동시 사용자 10명 조건에서 생성 API 평균 응답시간 중앙값은 27.1ms에서 12.0ms로 55.7% 감소했다.
- 같은 조건에서 생성 API p95 중앙값은 37ms에서 23ms로 37.8% 감소했다.
- 3회 모두 오류율 0%, 완료율 100%여서 빠른 접수 응답이 작업 유실로 이어지지 않았음을 확인했다.
- 비동기화는 계산 처리시간 개선이 아니라 HTTP 요청의 Critical Path 분리이며, E2E 완료시간은 별도 지표로 봐야 한다.
- 60요청 즉시 버스트에서 5%가 실패했으므로 Executor 포화 정책과 작업 거부 복구 방식은 추가 개선 대상이다.
- CPU, Heap, HikariCP 사용량은 이번 실행에서 수집하지 않아 관련 개선 수치로 주장하지 않는다.

## 이력서 문장 후보

> 백테스트 계산을 HTTP 요청 스레드에서 전용 비동기 Executor로 분리하고, JMeter 동시 요청 10건을 3회 반복 측정해 생성 API 평균 응답시간 중앙값을 27.1ms에서 12.0ms로 55.7%, p95를 37ms에서 23ms로 37.8% 단축했습니다. 작업 완료율 100%를 함께 검증했으며, 60건 즉시 버스트에서 확인한 Executor 포화 실패를 후속 개선 과제로 도출했습니다.
